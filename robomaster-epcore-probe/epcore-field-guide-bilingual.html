01

人员、场地与安全条件

人员分工

  • 操作员：运行脚本、操作网页、记录试次；站在行驶区外。
  • 安全观察员：只盯机器人和隔离区，负责叫停；不同时操作终端。
  • 记录员：拍摄高速录像、记试次编号和异常，可由第三人兼任。

任何运动测试都必须有人值守，并有可立即使用的人工急停。人工急停只用于救援；人工介入的试次记为失败，不计作系统自动停控成功。

必需器材

  • EP Core、充足电量、固定牢靠的代表性教学载荷；记录质量、位置和总质量。
  • 专用课堂 AP/路由器；关闭访客隔离和 AP client isolation，记录型号、频段、信道、机器人 IP 和信号情况。
  • 64 位 Python 3.8 venv；不要改系统 Python 3.12。
  • 需要网页测试时，准备目标手机、平板、笔记本，以及已启动的 bridge 和 web client。
  • 建议至少 120fps 的高速摄像机、三脚架、可见 LED/计时器、标尺或刻度地垫。
  • 平整干燥、封闭隔离的运动区；没有人员、易碎物或公共通道。
立即停测并判 FAIL / NO-GO未按预期停止、非预期加速/转向、人员进入隔离区、载荷松动、地面打滑、录像失效、急停不可用，或任何试次停稳超 1,000ms / 滑行超 30cm。不要为了凑满 30 次而继续风险测试。
02

建立一次测试批次

  1. 创建唯一批次目录，如 results/2026-11-09-classroom-a/，保存日志、录像、截图和手工表。
  2. 记录日期、场地、机器人型号/SN、固件、电量、载荷、速度档、SDK、Windows、浏览器与 AP 信息。
  3. 一次只连一台机器人。多台同网时指定 SN；用实际 SN 替换命令里的占位符： 
    .\.venv\Scripts\python.exe .\probe.py --sn "YOUR_ROBOT_SN" --observe-seconds 30
    单台可自动发现： 
    .\.venv\Scripts\python.exe .\probe.py --observe-seconds 30
  4. 记录主机网络接口和机器人 IP。录像、浏览器日志、主机日志使用同一试次编号；毫秒级时间以同一高速录像逐帧对齐。
  5. 更换机器人、载荷、地面、速度档或 AP 条件时，另开一组结果，不能混合统计。
A

只读连接与视频烟测

机器人保持静止；本阶段不发运动命令。
  1. 按 Python 环境章节建好 venv，确认 SDK 与 OpenCV import 成功。
  2. 确认机器人在 sta 组网模式，PC 接入同一个非访客 LAN；多机器人传入 --sn。
  3. 运行 30 秒观察命令。探针初始化 SDK、订阅底盘速度、启动 SDK 视频流并写出解码帧到达日志。
  4. 检查 JSONL/CSV 中有 connected、video_stream_started、连续 video_frame、observe_complete。连接失败、无帧或回调异常时先排查，不进入运动阶段。
  5. 重启探针，至少完成 3 次静止烟测，记录成功/失败和首帧到达时间。它只是连接诊断，不是浏览器 WSS/WebRTC 指标。
B

浏览器链路与延迟

仅在 bridge 与网页端已实现后执行。
当前包不能测出这些数字没有网页链路时，将状态写为“未测”，不要用 SDK 视频帧或 SDK 命令 RTT 代替。

浏览器连接成功率

Android Chrome、iOS/iPadOS Safari、Windows Edge/Chrome 分别做 10 次冷启动和 10 次 bridge 重启恢复。逐段记录本地网络权限、证书信任（如需要）、WSS、WebRTC ICE、首帧；失败要记阶段、错误码和截图，不隐藏重试。

视频 glass-to-glass：两条路径分开

  1. 把 LED 闪烁源或计时器放进机器人视野，用同一高速摄像机同时拍到真实事件和浏览器画面。
  2. 每种终端和 AP 条件分别测 h264-passthrough 与 transcode；记录分辨率、帧率、编码设置、bridge CPU、丢帧和冻结。
  3. 每路径至少 100 个可辨事件。计算：延迟 ms = (屏幕事件帧号 − LED事件帧号) / 摄像帧率 × 1000。固定角度、曝光和屏幕亮度，并记测量误差。
  4. 分别报告 p50、p95、最大值、有效样本数；目标 p95 ≤250ms。SDK 解码预览标为 sdk-decoded-only，不能冒充直通或转码。

控制输入到物理起动

  1. 只用已确认限速的网页控制；先确认松手停止/租约逻辑。
  2. 高速摄像同时拍到手指或鼠标动作、网页输入指示和机器人车轮/车体。起点是实际触摸/点击，终点是首次可辨物理运动。
  3. 每设备/网络条件至少 100 次有效起动；输入动作和速度档一致，试次间等车完全停稳。
  4. 报告 p50、p95、最大值；目标 p95 ≤150ms。ACK、RTT、遥测只作辅助。
C

低速实体制动基线

只在 A 阶段稳定、隔离区清空、观察员和人工急停在位后开始。首次只做一次短运动，确认方向、低速档、载荷和录像范围。

.\.venv\Scripts\python.exe .\probe.py --sn "YOUR_ROBOT_SN" --arm-motion --lease-ms 400 --speed 0.10

用实际 SN 替换占位符。观察员复核后，在提示处输入 ARM-ONE-TRIAL。脚本只发一条带 SDK timeout 的速度命令；速度不得超过 0.15m/s。单次表现异常时立即终止，不重试。

不要把它称为网页租约验收该试验不测网页 100ms 心跳，也不能证明 300–500ms 检测窗口。录像必须覆盖故障/命令、停止和完全静止；逐帧记故障 t0、检测 t1（如果可见）、停命令 t2（如果可见）、静止 t3，测 t3−t0、t3−t2 和滑行距离。
阶段测量口径目标
租约/检测100ms 心跳；比较丢失 3、4、5 次300–500ms
判定后制动停止命令至物理静止≤500ms
故障到完全静止以故障注入真实起点计算最大 ≤1,000ms
滑行距离故障点至最终静止，统一参考点最大 ≤30cm

以上都必须在运动中、低速默认档和代表性载荷下测；改变速度档要重新标定。人工急停介入的试次记失败。

D

故障注入：先过安全门

当前不能直接做运动中的进程/网络故障注入故障注入不是探针脚本功能。bridge 停止策略和机器人端或独立进程失效保护未验证前，不要在开放地面上杀进程、断 Wi-Fi 或让 Windows 睡眠；停止命令可能无法送达。缺少独立保护时，只做静止恢复测试，并将运动故障试验标为 blocked / NO-GO。

安全门通过之后，每类故障单独重复 30 次：控制租约超时/停止心跳、浏览器关闭/标签崩溃、Wi-Fi 断连/漫游、bridge 进程结束、Windows 睡眠/唤醒。

  1. 先静止时演练注入和恢复，确认每次只影响一段链路。
  2. 每次试验都使用低速默认档、相同代表性载荷、固定测试路线；高速录像开始后再运动。
  3. 将故障触发动作作为 t0；记录检测、停止命令、完全静止和滑行距离。
  4. 车体静止后恢复链路，确认重连不会恢复旧运动命令，再做下一次。逐次编号 01/30–30/30，不删失败和无效结果。
  5. 任何一次漏停、超时、超距或需要人工救援，立即停测并判 NO-GO；不得为凑样本继续冒险。

Windows 睡眠和 bridge 崩溃尤其危险。没有独立看门狗/刹车路径，不得在运动中测试这两类故障。

Python 3.8 独立环境

  1. 安装 64 位 CPython 3.8，并勾选 Python Launcher；不要覆盖系统 Python。
  2. 在探针目录 PowerShell 执行： 
    py -3.8 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
  3. 验证版本和依赖： 
    .\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -c "import robomaster, cv2; print(robomaster.__version__); print(cv2.__version__)"
    预期 SDK 为 0.1.1.68。如找不到 CPython 3.8 / Windows x64 wheel，记录完整错误并停止；不要静默从源码编译旧媒体扩展。
  4. 机器人与主机接入同一非访客 LAN，确认 AP 没有客户端隔离。Windows 防火墙只允许专用网络所需的本地流量，不向公用网络开放。

现场结束：停止视频和控制会话，确认车体静止；保存原始日志、表格和录像副本到团队位置。

01

People, test area, and safety conditions

Roles

  • Operator: runs the script, uses the browser, and records trials; stays outside the travel path.
  • Safety observer: watches only the robot and exclusion zone; calls the stop and does not operate the test computer.
  • Recorder: captures high-speed video, trial IDs, and anomalies; a third person may fill this role.

Never run a motion test unattended. Keep a manual emergency stop immediately available. It is for rescue only; any trial requiring it is a failure, not an automatic safety stop.

Required equipment

  • EP Core, charged battery, secured representative teaching payload; record mass, position, and total load.
  • Dedicated classroom AP/router; disable guest isolation and AP client isolation. Record model, band, channel, robot IP, and signal conditions.
  • 64-bit Python 3.8 venv. Do not change system Python 3.12.
  • For browser testing, prepare target phones/tablets/laptops and a running bridge and web client.
  • High-speed camera (120fps or faster recommended), tripod, visible LED/timer, and ruler or marked floor mat.
  • Flat, dry, enclosed test area with a clear exclusion zone; never test in a class or public corridor.
Stop immediately and mark FAIL / NO-GOUnexpected motion or failure to stop, anyone entering the exclusion zone, loose payload, slippery floor, failed recording, unavailable emergency stop, or any trial exceeding 1,000ms / 30cm. Do not continue risky trials just to reach 30 samples.
02

Create a test run

  1. Create a unique run folder, e.g. results/2026-11-09-classroom-a/. Keep logs, recordings, screenshots, and worksheets together.
  2. Record date, site, robot model/SN, firmware, battery, payload, speed profile, SDK, Windows, browser, and AP details.
  3. Connect to one robot at a time. For multiple robots on the same LAN, specify the SN. Replace the placeholder with the actual serial number: 
    .\.venv\Scripts\python.exe .\probe.py --sn "YOUR_ROBOT_SN" --observe-seconds 30
    For one robot, automatic discovery is available: 
    .\.venv\Scripts\python.exe .\probe.py --observe-seconds 30
  4. Record the PC network interface and robot IP. Use the same trial ID for video and logs; align millisecond measurements frame by frame in one high-speed recording rather than relying on device wall clocks.
  5. Start a separate result group when the robot, payload, floor, speed profile, or AP condition changes. Do not mix groups.
A

Stationary connection and video smoke check

Keep the robot still; send no motion command in this stage.
  1. Set up the Python 3.8 venv and confirm the SDK and OpenCV imports work.
  2. Confirm the robot is in sta mode and the PC is on the same non-guest LAN. Pass --sn when multiple robots are present.
  3. Run the 30-second observation command. The probe initializes the SDK, subscribes to chassis velocity, starts SDK video, and logs decoded frame arrivals.
  4. Check the JSONL/CSV for connected, video_stream_started, repeated video_frame, and observe_complete events. If connection fails, no frames arrive, or a callback errors, troubleshoot before any motion test.
  5. Restart the probe for at least three stationary checks. Record success/failure and first-frame arrival. This is connection diagnostics, not a browser WSS/WebRTC metric.
B

Browser connectivity and latency

Run only after the bridge and web client are implemented.
The current package cannot produce these metricsIf the browser path is not implemented, record “not measured.” Do not substitute SDK frame arrival or SDK command RTT.

Browser connection success rate

For Android Chrome, iOS/iPadOS Safari, and Windows Edge/Chrome, run 10 cold starts and 10 bridge-restart recoveries per device. Record local-network permission, certificate trust if required, WSS, WebRTC ICE, and first frame separately. Preserve the failure stage, error code, and screenshot; do not hide retries.

Video glass-to-glass: measure both paths separately

  1. Place a visible blinking LED or timer in the robot camera view. Use one high-speed camera to capture both the real event and the browser screen.
  2. For each device and AP condition, run h264-passthrough and transcode separately. Record resolution, frame rate, encoding settings, bridge CPU, dropped frames, and freezes.
  3. Collect at least 100 visible events per path. Calculate latency ms = (screen event frame − LED event frame) / camera frame rate × 1000. Keep camera angle, exposure, and screen brightness fixed; note measurement error.
  4. Report p50, p95, maximum, and valid sample count for each path. Target p95 ≤250ms. Label an SDK preview sdk-decoded-only; do not call it passthrough or transcode.

Control input to physical motion

  1. Use only browser control with verified speed limiting; first confirm release/stop and lease behavior.
  2. Record the operator's finger/mouse action, browser input indicator, and robot wheels/body in one high-speed view. Start at actual touch/click; stop at first visible physical motion.
  3. Collect at least 100 valid starts per device/network condition. Keep input duration and speed profile consistent; wait for a complete stop between trials.
  4. Report p50, p95, and maximum. Target p95 ≤150ms. ACK, RTT, and telemetry are supporting data only.
C

Low-speed physical stop baseline

Proceed only after Stage A is stable and the exclusion zone, observer, and manual emergency stop have been checked. Start with one short movement to confirm direction, low-speed profile, payload, and camera framing.

.\.venv\Scripts\python.exe .\probe.py --sn "YOUR_ROBOT_SN" --arm-motion --lease-ms 400 --speed 0.10

Replace the placeholder with the actual SN. After the observer confirms the clear zone, enter ARM-ONE-TRIAL at the prompt. The script sends one speed command with an SDK timeout; do not exceed 0.15m/s. Stop immediately if the first trial behaves unexpectedly.

D

Fault injection: pass the safety gate first

Do not inject process/network faults during open-floor motion yetFault injection is not implemented by this probe. Until bridge stop behavior and a robot-side or independent process fail-safe are verified, do not kill the process, disconnect Wi-Fi, or put Windows to sleep while moving. The stop command may not reach the robot. Without independent protection, perform recovery checks only while stationary and mark motion fault testing blocked / NO-GO.

After the safety gate passes, run 30 separate trials for each fault: control lease/heartbeat loss, browser close or tab crash, Wi-Fi disconnect/roam, bridge process exit, and Windows sleep/wake.

  1. First rehearse injection and recovery while stationary; confirm which link is affected and test only one fault at a time.
  2. For every motion trial, use the default low-speed profile, same representative payload, and fixed test route. Start high-speed recording before motion.
  3. Use the visible fault-trigger action as t0. Record detection, stop command, full rest, and coast distance.
  4. Inject one fault at a time. After the robot stops, restore the link and confirm reconnect cannot resume an old motion command. Number every attempt 01/30 through 30/30; retain failed and invalid results.
  5. Any missed stop, over-limit time/distance, or rescue intervention means stop and NO-GO. Do not continue just to fill the sample count.

Windows sleep and bridge crashes are especially hazardous. Never test these during motion without an independent watchdog/braking path.

Isolated Python 3.8 environment

  1. Install 64-bit CPython 3.8 and the Python Launcher. Do not replace system Python.
  2. In PowerShell, from the probe directory: 
    py -3.8 -m venv .venv
.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
  3. Verify the interpreter and dependencies: 
    .\.venv\Scripts\python.exe --version
.\.venv\Scripts\python.exe -c "import robomaster, cv2; print(robomaster.__version__); print(cv2.__version__)"
    Expected SDK version: 0.1.1.68. If no CPython 3.8 / Windows x64 wheel is available, capture the full error and stop; do not silently compile the legacy media extension from source.
  4. Put the robot and PC on the same non-guest LAN; confirm client isolation is off. Allow only required local traffic on the Windows Private network profile, never the Public profile.
