# RoboMaster EP Core 真机实测指南

本文用于在教室现场对 EP Core 做分阶段技术探针。它把“SDK 能连接/出图/下发命令”与“网页 bridge 的端到端性能和失联安全”分开记录。后者需要网页客户端和 bridge 已经实现；当前 `probe.py` 本身不实现 WSS、WebRTC、原始 H.264 relay，也不实现浏览器心跳租约。

验收口径采用项目试运行目标：视频 p95 ≤250ms，控制输入到物理起动 p95 ≤150ms；安全故障须 30/30 触发停控，故障至完全静止最大值 ≤1000ms，最大滑行距离 ≤30cm。它们是本项目低速默认档、代表性载荷下的工程 go/no-go 目标，不是 DJI 或 ISO 的保证值。每个速度档都要单独重新标定。

## 0. 先判断当前能测到什么

| 能力 | 当前探针包 | 需要另备/已实现的东西 |
|---|---|---|
| SDK 连接、底盘速度遥测 | 可以观察 | 机器人、Python 3.8 环境、课堂局域网 |
| SDK 解码视频帧到达 | 可以观察帧数和到达事件 | 它不是端到端延迟，也不是浏览器视频 |
| 单条 SDK 速度命令的 timeout | `--arm-motion` 可做一次有人值守的低速试验 | 空旷测试区、代表载荷、观察员、高速录像 |
| 浏览器 WSS / WebRTC / 浏览器控制 | 当前探针不支持 | 可运行的本地 bridge 和网页客户端 |
| H.264 直通 vs 转码、端到端视频延迟 | 当前探针不支持 | 两条 relay 路径、目标终端、同步高速录像 |
| 浏览器心跳租约、断网/进程崩溃/睡眠安全 | 当前探针不支持 | bridge 租约实现、独立失效保护和专门风险评估 |

**不要把 `--lease-ms` 当成已实现的网页租约测试。** 它只是 SDK `drive_speed(timeout=...)` 的单条命令超时试验；它依赖 Windows 上的 Python 进程继续运行，停止命令仍须经网络发到机器人。进程被杀、电脑睡眠或 Wi-Fi 断开时，不能假设车体会自动停。DJI SDK 的 `sta` 模式和可选 `sn` 参数可用于连接/选择机器人；视频和控制仍需按 SDK 文档接入。参考 [DJI RoboMaster SDK 源码](https://github.com/dji-sdk/RoboMaster-SDK) 与[连接文档](https://github.com/dji-sdk/RoboMaster-SDK/blob/master/docs/source/text_sdk/connection.rst)。

## 1. 人员、场地和器材

### 人员分工

- **测试操作员**：运行脚本、操作浏览器、记录试次，不进入机器人行驶路径。
- **安全观察员**：全程盯住机器人和障碍区，负责叫停；不兼任脚本操作。
- **记录员**（可由非操作时的第三人兼任）：负责高速录像、试次编号、标记结果和异常。

任何运动测试都不能无人值守。现场必须有可立即使用的人工急停手段；人工急停是救援手段，不得将人工急停介入后的试次记成系统自动停控成功。

### 必需器材

- EP Core、充足电量、固定牢靠的代表性教学载荷；记录载荷质量、安装位置和总质量。
- 与测试主机在同一专用局域网的课堂 AP/路由器；关闭访客隔离和 AP client isolation。记录型号、固件、频段、信道、SSID、机器人 IP 和信号条件。
- 64 位 Python 3.8 独立 venv、当前探针包；不要改动系统 Python 3.12。
- 目标手机/平板/笔记本及浏览器；如果测网页链路，需要已启动的 bridge 和 web client。
- 高速摄像机，建议至少 120fps，越高越能减少时间量化误差；三脚架、可见 LED/计时器、标尺或带刻度地垫。
- 机器人运动测试区：平整干燥地面、封闭/隔离、路径无人员与易碎物，四周留足余量；初测不得在学生课堂或公共通道进行。

### 绝对停测条件

出现以下任一项，操作员立即停止命令，观察员用人工急停救援，记录为 **FAIL/NO-GO** 并停止本轮运动测试：

1. 机器人没有按预期停止、出现非预期转向/加速，或连续控制失联。
2. 任何人员或物品进入测试隔离区，载荷松动，地面打滑，电量或温度异常。
3. 录像中断、时间点不可辨，急停不可用，或操作员/观察员失去通信。
4. 任一故障试次停稳超过 1000ms，或滑行超过 30cm；即使其余试次通过也立即停止，不再继续重复同一风险测试。

## 2. 建立一次测试批次

1. 在探针目录内建立唯一批次文件夹，例如 `results/2026-11-09-classroom-a/`。把脚本每次生成的 JSONL、CSV、录像、截图和手工表放在同一批次目录中。
2. 在 [验收清单](acceptance-checklist.md) 记录日期、场地、机器人型号/序列号、固件、电量、载荷、SDK 版本、Windows 版本、路由器/AP 和浏览器设备版本。
3. 一次只连接/测试一台机器人。多台同网时用该机器人 SN 启动：

   ```powershell
   .\.venv\Scripts\python.exe .\probe.py --sn "YOUR_ROBOT_SN" --observe-seconds 30
   ```

   单台/自动发现：

   ```powershell
   .\.venv\Scripts\python.exe .\probe.py --observe-seconds 30
   ```

4. 检查目标 SN、机器人 IP、Wi-Fi 接口和设备时间。录像、主机日志和浏览器日志先采用同一批次/试次编号；不要只依赖各设备墙上时钟做毫秒级计算。
5. 记录测试前电量、速度档、载荷和 AP 信号。更换机器人、载荷、地面、轮胎状态、速度档或 AP 配置时，开启新分组，不能混合统计。

## 3. 阶段 A：只读连接和视频烟测

此阶段机器人保持静止、控制器无运动输入。

1. 按 [Python 3.8 环境步骤](python-38-setup.md) 建好 venv，并确认 SDK 与 OpenCV import 验证成功。
2. 确认机器人处于 `sta` 组网模式，测试 PC 接到同一非访客 LAN；多机器人时传 `--sn`。
3. 运行 30 秒观察命令。该脚本会初始化 SDK、订阅底盘速度、启动 SDK 视频流并记录 SDK 解码帧到达事件，然后自动关闭会话。
4. 检查输出：有 `connected`、`video_stream_started`、持续的 `video_frame` 事件和 `observe_complete`；检查 CSV/JSONL 文件存在且非空。若连接失败、帧为空或回调错误，先停止并排查网络、SN、摄像头流占用和 SDK 依赖，不做运动。
5. 重启探针再做至少 3 次只读连接，记录每次成功/失败、连接耗时和第一帧到达时间。这个连接耗时只是烟测统计，不是三项 go/no-go 中的浏览器 WSS/WebRTC 延迟。

## 4. 阶段 B：网页路径和延迟测量

**此阶段只有在 WSS/WebRTC bridge 和网页端已经实现后才能做。** 当前探针包不能给出下面的浏览器指标；不要用 SDK 帧到达日志填入网页测量表。

### 4.1 浏览器连接成功率

每种目标终端（Android Chrome、iOS/iPadOS Safari、Windows Edge/Chrome）分别做 10 次冷启动和 10 次 bridge 重启恢复：

1. 完全关闭浏览器页/应用，按同一流程重新打开本地网页。
2. 记录本地网络权限、证书信任（若需要）、WSS 握手、WebRTC ICE、首帧显示分别是否通过；失败要写出卡在哪一阶段及错误码/截图。
3. 冷启动阶段记录 10 次；bridge 正常重启后记录恢复阶段 10 次。不要把失败重试隐藏在“最终成功”里。

### 4.2 视频 glass-to-glass：直通、转码分开跑

1. 在机器人相机视野内放置可见 LED 闪烁源或毫秒计时器；高速摄像机同一画面同时拍到真实源和客户端屏幕。固定拍摄角度、帧率、曝光和屏幕亮度。
2. 对每一终端、AP/信号条件，分别完整跑 `h264-passthrough` 和 `transcode`。记录 relay 路径名、分辨率、帧率、编码设置、主机 CPU 峰值、丢帧/冻结、WSS/ICE 成败。
3. 至少收集 100 个可辨事件。按录像帧数换算每个事件的延迟：`延迟(ms) = (客户端画面事件帧号 - 真实 LED 事件帧号) / 高速摄像帧率 × 1000`。如果有可见的显示扫描/曝光偏差，写进测量误差。
4. 每条路径分别报告 p50、p95、最大值、有效样本数和丢帧/冻结次数。目标为 p95 ≤250ms；少于 100 个有效事件的结果标记为未完成。
5. 若网页画面未接入、路径不明或实际是 SDK 解码预览，标 `sdk-decoded-only`，不能伪称直通或转码结果。

### 4.3 控制输入到物理起动

1. 仅使用已验证限速的网页控制；先确认松手会发停止/心跳租约行为按设计执行。
2. 高速摄像机同时拍到操作员手指/鼠标动作、网页输入指示，以及机器人轮子/车体；测量输入发生至车体首次可辨运动的时间。命令 ACK、WSS RTT、底盘遥测只作为辅助，不代替物理起动。
3. 每设备/网络条件至少 100 次有效起动；每次用统一短促输入和固定速度档，试次间待车体完全停稳。
4. 报告 p50、p95、最大值和样本数，目标 p95 ≤150ms。任何意外方向/持续运动立即停测。

## 5. 阶段 C：低速实体制动基线

只有 A 阶段稳定且测试区/观察员/人工急停检查全部通过后才开始。首次只做极短单次运动，确认方向、速度档和录像视野正确；确认前不做重复测试。

1. 在相机视野中放置带刻度标尺，车体和轮子可辨。录像至少覆盖起动前、故障发生、停止、车体完全静止之后。
2. 完成 30 秒静止烟测后，运行单次低速 SDK timeout 试验：

   ```powershell
   .\.venv\Scripts\python.exe .\probe.py --sn "YOUR_ROBOT_SN" --arm-motion --lease-ms 400 --speed 0.10
   ```

   在确认提示输入 `ARM-ONE-TRIAL` 前，观察员要确认隔离区已清空；速度不得超过 0.15m/s，并按现场低速默认档使用。`--arm-motion` 每次只发一条速度命令。若单次运动方向、时长或制动表现异常，立即结束，不做下一次。
3. 此试验只证明当下 SDK 单条速度命令 timeout 路径的表现；它不测网页心跳检测 300–500ms，也不等同于“故障发生→停稳”完整租约试验。物理停稳必须看高速录像。
4. 从录像逐帧标注：运动输入/故障注入、预期检测/租约到期（如果有该实现）、停止命令发出（若可观测）、车体最后一次运动。记录故障至停稳总时间、停止命令至停稳时间和最大滑行距离。
5. 安全初测达标后，真实 bridge 租约功能就绪时，再在低速档和带载条件下按每种故障 30 次计划测量。每次先停车归零、确认场地，再开始下一次；禁止自动连续跑 30 次。

**租约口径：** 实际网页实现应明确 100ms 心跳、连续 3/4/5 次丢失的配置差别和检测窗口。分别量故障发生至检测、检测/判定至停止命令、停止命令至物理静止；总时间最大值必须 ≤1000ms，且检测/租约窗口目标 300–500ms、制动到静止 ≤500ms。三段加总要用同一故障起点计算，不能用命令 ACK 代替物理停稳。

## 6. 阶段 D：故障注入（严格安全门）

故障注入不是当前脚本的功能。**在 bridge 停止策略、机器人端或独立进程失效保护没有验证前，不要在开放地面运动中杀进程、断 Wi-Fi 或让 Windows 睡眠。** 这些事件可能让停止命令发不出去。应先在有围挡的封闭试验区验证独立救援停止路径，安排观察员持有救援控制；如果缺少独立失效保护，只能先做非运动状态的链路/进程恢复测试，运动故障测试标记为 **blocked / NO-GO**。

对安全门通过的场景，逐个故障类型做 30 次：

1. **先静止验证注入动作**：比如关浏览器页、切断测试终端 Wi-Fi、停止 bridge、系统睡眠/唤醒。在不运动时确认操作会影响哪一段链路、如何恢复；每次测试只注入一个故障。
2. **准备一次运动试次**：低速默认档、同一代表性载荷、固定路线和电量区间；高速录像已开始，操作员和观察员已就位。
3. **记录真实故障起点**：以可辨的故障触发动作/录像标记为 t0；不要用“发现车停了”的时刻当故障起点。
4. **注入单一故障**：控制 lease/停止心跳、浏览器关闭或标签崩溃、Wi-Fi 断连/漫游、bridge 进程结束、Windows 睡眠/唤醒逐类单独测试。每次都确保除目标故障外其他链路保持正常。
5. **等停稳并测距**：记录检测、停止命令、最后运动帧，测量故障点至最终静止点的车体前沿位移。救援急停触发则此试次为失败，立即终止该批。
6. **试次复位**：车体完全静止后恢复网络/进程，确认控制连接没有自动恢复成运动状态，再开始下一次。记录编号 01/30 至 30/30，包括失败、漏测和无效试次；不得删掉不利结果。

对每一类故障都要分别达到 30/30 观察到自动停控；任一漏停、最大总时间 >1000ms 或滑行 >30cm，立即判 NO-GO。温度、地面、载荷、速度档变化明显时另开批次。Windows 睡眠/桥接崩溃发生在真实运动中尤其危险；没有独立看门狗/刹车路径时不得尝试运动注入。

### 每次安全试次一行

| 批次/机器人/SN | 故障类型 | 次数 | 速度档/载荷 | 故障 t0 | 检测 t1 | 发停命令 t2 | 完全静止 t3 | 故障→静止 ms | 停命令→静止 ms | 滑行 cm | 自动停控? | 录像文件 | 备注 |
|---|---|---:|---|---:|---:|---:|---:|---:|---:|---:|---|---|---|
|  |  | 01/30 |  |  |  |  |  | t3−t0 | t3−t2 |  | 是/否 |  |  |

以录像帧率 `F` 计算时间差：`毫秒 = 帧差 / F × 1000`。例如 240fps 每帧约 4.17ms；报告实际帧率和取帧误差。滑行距离以地面标尺读数为准，录像做复核；记录车体统一参考点（推荐车体前沿或轮轴中心），整轮批次不可换参考点。

### 汇总时必须给出

- 视频：直通/转码各自有效样本数、p50/p95/max、冻结/丢帧和 CPU 峰值。
- 控制：每设备有效样本数、p50/p95/max；把网页触摸→车动和命令/遥测辅助时间分列。
- 安全：每故障类型触发成功数/30、最大故障到停稳时间、最大制动时间、最大滑行距离、异常和救援急停次数。
- 连接：每平台冷启动成功率、bridge 恢复成功率、失败阶段。
- 未完成项：明确写 **未测 / blocked / 无有效样本**，不得留空让人误认通过。

## 8. 最终 go/no-go

- **GO（仅进入下一阶段试用）**：每个目标平台的浏览器连接/恢复路径完成规定次数；视频两路径和控制输入到运动完成有效样本且达到阈值；所有安全故障 30/30 自动停控、最大总停稳 ≤1000ms、最大滑行 ≤30cm；数据和录像可复核。
- **NO-GO**：任一安全触发失败、最大时间/距离超标、任一目标设备无法建立所需路径，或出现无法解释的异常运动。
- **未判定**：组件还没实现、样本数不足、录像无法测量或安全隔离不够。未判定不能写成通过，先补实现/条件再复测。

完成后停止视频流和控制会话，确认车体静止，断开测试控制终端；检查批次目录有原始日志、测量表和录像副本，再备份到团队位置。
